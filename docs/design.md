# Secret Santa Bot — Technical Design Document

**Версия:** 0.3 (MVP)  
**Формат:** Markdown  
**Предлагаемый стек:** Go, PostgreSQL, Telegram Bot API  
**Статус:** Draft

## 1. Цель и концепция

Разработать Telegram-бота для организации игры «Тайный Санта» между пользователями, объединёнными во **внутренние группы приложения**. Эти группы **не являются Telegram-группами или чатами**: Telegram используется как пользовательский интерфейс, средство авторизации по Telegram User ID и канал личных уведомлений.

Один бот обслуживает много независимых групп. Участник может состоять в нескольких группах, а каждая группа может проводить несколько игр в разные годы.

### Ключевые требования

- Создание внутренней группы и приглашение в неё по deeplink вида `https://t.me/<bot_username>?start=join_<token>`.
- Просмотр собственных групп, их состава и текущей игры.
- Роли владельца, администратора и участника.
- Создание и настройка отдельной игры внутри группы.
- Подтверждение участия в игре; специальные правила для новых членов группы.
- Случайная жеребьёвка, в которой каждый дарит одному человеку и получает от одного.
- Личное уведомление о назначенном получателе подарка.
- Повторный просмотр своего жребия.
- Добавление нового участника после жеребьёвки и при необходимости пережеребьёвка.
- Конфиденциальность назначений, устойчивость к повторным командам и сбоям доставки.

## 2. Доменная модель

| Сущность | Назначение |
|---|---|
| `User` | Пользователь, идентифицируемый по Telegram User ID. |
| `Group` | Внутреннее сообщество пользователей приложения. |
| `GroupMember` | Членство в группе с ролью и статусом. |
| `GroupInvite` | Ссылка-приглашение в группу, которую можно отозвать. |
| `Game` | Конкретная игра внутри группы, например «Тайный Санта 2026». |
| `GameParticipant` | Участие пользователя в конкретной игре и его подтверждение. |
| `Draw` | Версия жеребьёвки. |
| `Assignment` | Связь «даритель → получатель» в версии жеребьёвки. |
| `NotificationOutbox` | Задача на отправку сообщения через Telegram. |
| `AuditLog` | Журнал административных действий без раскрытия назначений. |

**Важное разграничение:** вступление в группу и участие в конкретной игре — разные операции. Членство в группе сохраняется между играми.

Для MVP допускается **не более одной текущей (не завершённой и не отменённой) игры на группу**. Это устраняет неоднозначность при автоматической регистрации по групповому приглашению.

## 3. Роли и права

### Owner

- Создаёт группу и получает роль владельца.
- Управляет администраторами и передачей владения.
- Может переименовывать и архивировать группу.
- Имеет все права Admin.

### Admin

- Видит состав группы, создаёт, отзывает и обновляет приглашения.
- Управляет участниками группы и игры.
- Создаёт игру и изменяет параметры.
- Закрывает регистрацию, запускает жеребьёвку.
- Приглашает или добавляет участников после жеребьёвки.
- Подтверждает полную пережеребьёвку.
- Видит статусы отправки уведомлений, **но не чужие назначения**.

### Member

- Видит собственные группы и общий список их участников.
- Подтверждает или отклоняет участие в игре.
- Видит свои назначения, сроки и параметры игры.
- Может выйти из группы; последствия для активной жеребьёвки обрабатываются отдельно.

Права всегда проверяются на backend, а не только через видимость кнопок.

## 4. Правила регистрации в игре

**Согласованное продуктовое правило:** существующие участники группы подтверждают участие в каждой новой игре отдельно. **Пользователь, впервые вступивший во внутреннюю группу по deeplink в период открытой регистрации, автоматически считается подтвердившим участие в её текущей игре.**

| Сценарий | Результат |
|---|---|
| Новый пользователь впервые вступает в группу по deeplink; регистрация в игре открыта | Создаётся `GroupMember` и `GameParticipant(CONFIRMED)` автоматически. |
| Новый пользователь впервые вступает по deeplink; текущей игры нет | Создаётся только `GroupMember`. |
| Пользователь уже состоит в группе; создаётся новая игра | Участие по умолчанию `PENDING`; требуется отдельное подтверждение. |
| Участник отказался от игры | `DECLINED`; членство в группе сохраняется. |
| Пользователь повторно открывает ссылку, уже являясь членом группы | Идемпотентно; предыдущий отказ или подтверждение не изменяется. |
| Новый пользователь вступает после жеребьёвки | Членство в группе создаётся; согласие на участие считается данным, но **в активную жеребьёвку его добавляет администратор**. До этого жребий не назначен. |
| Пользователь вступает во время закрытой регистрации до жеребьёвки | Становится членом группы, но не включается в закрытый список участников автоматически. |

Для состояния после жеребьёвки удобно хранить **подтверждение участия отдельно от факта включения в жеребьёвку**:

- `game_participants.status = CONFIRMED` — пользователь согласен участвовать.
- `game_participants.assignment_state = AWAITING_ASSIGNMENT | ASSIGNED | NOT_APPLICABLE` — его статус относительно текущего розыгрыша.

Таким образом новый член группы после жеребьёвки может быть `CONFIRMED + AWAITING_ASSIGNMENT`, не нарушая инварианты действующей жеребьёвки. Администратор видит его в списке ожидающих добавления.

**Ссылка принадлежит группе, а не игре.** Одна ссылка может использоваться между сезонами, пока не отозвана и пока выполняются ограничения приглашения. При вступлении действуют правила текущей игры.

## 5. Основные пользовательские сценарии

### 5.1. Первый запуск

1. Пользователь открывает личный диалог с ботом и нажимает Start.
2. Backend создаёт или обновляет `User` по Telegram ID.
3. Бот показывает кнопки «Мои группы», «Создать группу», «Помощь».

Бот обычно не может отправить личное сообщение пользователю, пока тот сам не инициировал чат; регистрация через личный deeplink решает это для новых участников.

### 5.2. Создание группы

1. Пользователь нажимает «Создать группу».
2. Вводит имя, например «Друзья».
3. Backend создаёт группу и членство с ролью `OWNER`.
4. Создаёт безопасный токен приглашения.
5. Бот показывает ссылку и меню управления группой.

Пример: `https://t.me/SecretSantaBot?start=join_A1B2C3` (токен иллюстративный).

### 5.3. Вступление в группу через deeplink

1. Пользователь открывает ссылку и запускает бота.
2. Бот извлекает `join_<token>`, проверяет валидность и срок действия приглашения.
3. Показывает название группы и кнопку «Вступить».
4. По подтверждению в транзакции создаёт членство в группе.
5. Если это **первое** вступление и игра находится в `REGISTRATION`, создаёт подтверждённое участие в игре.
6. Бот сообщает об успешном вступлении и, при наличии, о включении в игру.

**Пример сообщения:**

> 🎄 Ты присоединился к группе «Друзья»!  
> Ты автоматически зарегистрирован в игре «Тайный Санта 2026».  
> Участников: 8  
> [Посмотреть участников] [Отказаться от участия]

### 5.4. Создание новой игры

1. Owner/Admin выбирает группу и нажимает «Создать игру».
2. Указывает название, бюджет (необязателен), срок регистрации и дату обмена.
3. Игра становится `REGISTRATION`.
4. Существующие члены группы получают возможность подтвердить участие; их участие не становится подтверждённым автоматически.
5. Новые члены, впервые вступающие через приглашение во время открытой регистрации, подтверждаются автоматически.

### 5.5. Управление участниками

Администратор видит отдельно:

- Подтвердили участие (`CONFIRMED`).
- Ожидают решения (`PENDING`).
- Отказались (`DECLINED`).
- Ожидают включения в уже состоявшуюся жеребьёвку (`AWAITING_ASSIGNMENT`).

В меню группы показывается полный состав членов независимо от текущей игры.

### 5.6. Старт жеребьёвки

1. Администратор открывает игру и запускает жеребьёвку.
2. Backend проверяет права, статус игры и число подтверждённых участников (MVP: не менее 3).
3. Администратор подтверждает действие.
4. В транзакции формируются и сохраняются назначения, новая версия Draw и задачи отправки уведомлений.
5. Игра переходит в `DRAWN`.
6. Outbox Worker отправляет каждому участнику сообщение с его получателем.

**Пример сообщения:**

> 🎁 Твой жребий готов!  
> Игра: Тайный Санта 2026  
> Ты даришь подарок: **Анне**  
> Бюджет: до 2 000 ₽  
> Обмен: 25 декабря  
> [Посмотреть получателя]

### 5.7. Добавление человека после жеребьёвки

Новый человек может вступить в **группу** в любой момент, но это не должно молча менять уже разосланные назначения.

1. Пользователь вступает в группу по deeplink.
2. Система фиксирует его согласие на текущую игру и состояние `AWAITING_ASSIGNMENT`.
3. Администратор получает индикатор «Ожидают добавления: 1».
4. Администратор выбирает «Добавить в жеребьёвку».
5. Бот предупреждает, какие последствия возникнут для уже уведомлённых участников (без раскрытия жребиев).
6. После подтверждения создаётся новая версия жеребьёвки и соответствующие уведомления.

#### Режим A: минимальная вставка

Было:

```text
Аня → Борис → Виктор → Аня
```

Стало:

```text
Аня → Борис → Дмитрий → Виктор → Аня
```

Изменяется ровно **одно существующее назначение**: у Бориса новый получатель. Дмитрий получает Виктора. Другие назначения остаются прежними.

Такой режим работает для **одного общего цикла** без дополнительных ограничений на пары. При этом прежнее назначение Бориса уже могло быть прочитано, поэтому бот обязан явно предупредить о его изменении.

#### Режим B: полная пережеребьёвка

Администратор может инициировать перераспределение всех участников. Операция требует отдельного подтверждения и рассылки новых актуальных жребиев.

### 5.8. Выход из группы

До жеребьёвки выход удаляет (или деактивирует) членство и исключает человека из списка участников текущей игры. После жеребьёвки выход не должен автоматически разрывать распределение: требуется явное административное разрешение ситуации (удаление с корректировкой либо полная пережеребьёвка).

## 6. Состояния

### Game

```text
DRAFT → REGISTRATION → LOCKED → DRAWN → COMPLETED
                        ↘ CANCELLED
```

- `DRAFT` — игра создана, но регистрация ещё не открыта.
- `REGISTRATION` — набор и подтверждение участников.
- `LOCKED` — регистрация закрыта, но жеребьёвка ещё не проведена.
- `DRAWN` — назначения созданы и актуальны.
- `COMPLETED` — игра завершена.
- `CANCELLED` — игра отменена.

### GameParticipant

- `PENDING` — существующий член группы ещё не подтвердил участие в новой игре.
- `CONFIRMED` — участие подтверждено (вручную или автоматически при первом вступлении по ссылке).
- `DECLINED` — отказ от участия.

Отдельно `assignment_state`: `NOT_APPLICABLE`, `AWAITING_ASSIGNMENT`, `ASSIGNED`. Его можно вычислять из активного Draw, но для простого интерфейса допустима денормализация при строгом обновлении внутри транзакции.

### Draw

- `ACTIVE` — актуальная версия.
- `INVALIDATED` — старая версия, заменённая новым розыгрышем.

## 7. Алгоритм жеребьёвки

### Random Single Cycle (MVP)

1. Получить подтверждённых участников игры, включаемых в жеребьёвку.
2. Перемешать список с криптографически стойким генератором случайности.
3. Назначить каждому следующего в списке.
4. Последнему назначить первого.

**Инварианты:**

- У каждого участника ровно один получатель.
- У каждого участника ровно один даритель.
- Никто не назначается самому себе.
- Все участники образуют один замкнутый цикл.
- В игре не возникает взаимных пар из двух участников.

Это равномерный выбор **среди одиночных циклов**, но не среди всех перестановок без фиксированных точек (дерранжировок). Для MVP такое правило принимается сознательно.

### Транзакционный запуск

```text
BEGIN
SELECT game FOR UPDATE
проверка статуса, полномочий и состава
генерация новой версии Draw
INSERT assignments
INSERT notification_outbox
UPDATE game.active_draw_id, game.status
COMMIT
```

Повторный callback либо параллельный запрос не должен создать второй Draw. Для новой версии при пережеребьёвке требуется отдельная явная команда.

## 8. Архитектура

**Подход:** модульный монолит, без дополнительных брокеров и микросервисов на MVP.

```text
Telegram users (личный чат с ботом)
            |
            v
    Telegram Bot API
            |
            v
    Telegram Handler (Go)
            |
     +------+------+-------------------+
     |             |                   |
     v             v                   v
 Group Service  Game Service       Draw Service
     |             |                   |
     +-------------+-------------------+
                   |
                   v
              PostgreSQL
                   |
                   v
          Notification Outbox
                   |
                   v
            Worker (Go)
                   |
                   v
            Telegram Bot API
```

**Модули:**

- `telegram` — обработка updates, команд, callback и deeplink.
- `users` — пользовательские данные Telegram.
- `groups` — группы, членство, роли, инвайты.
- `games` — жизненный цикл игры и подтверждения.
- `draws` — алгоритм жеребьёвки, версии и изменения состава.
- `notifications` — сообщения, retry, мониторинг доставки.
- `storage` — SQL-запросы, миграции, транзакции.

**Стек:** Go, `pgx` + `sqlc` (или ручные запросы), PostgreSQL, `slog`, `goose`/`golang-migrate`, Docker Compose, GitHub Actions. Для локальной разработки — long polling, в production предпочтительно HTTPS webhook.

## 9. Модель БД (проект)

```text
users
  id PK
  telegram_id BIGINT UNIQUE NOT NULL
  username NULL
  display_name
  dm_started_at
  created_at, updated_at

groups
  id PK
  name
  owner_id FK -> users.id
  status
  created_at

group_members
  group_id FK -> groups.id
  user_id FK -> users.id
  role ENUM(OWNER, ADMIN, MEMBER)
  status
  joined_at
  UNIQUE(group_id, user_id)

group_invites
  id PK
  group_id FK -> groups.id
  token_hash UNIQUE
  created_by FK -> users.id
  expires_at NULL
  max_uses NULL
  used_count
  revoked_at NULL

games
  id PK
  group_id FK -> groups.id
  name
  status
  budget NULL
  registration_deadline NULL
  exchange_at NULL
  active_draw_id NULL
  created_by
  created_at

game_participants
  id PK
  game_id FK -> games.id
  user_id FK -> users.id
  status ENUM(PENDING, CONFIRMED, DECLINED)
  assignment_state ENUM(NOT_APPLICABLE, AWAITING_ASSIGNMENT, ASSIGNED)
  registered_at
  confirmed_at NULL
  UNIQUE(game_id, user_id)

draws
  id PK
  game_id FK -> games.id
  version
  status
  created_by
  created_at
  UNIQUE(game_id, version)

assignments
  id PK
  draw_id FK -> draws.id
  giver_participant_id FK -> game_participants.id
  receiver_participant_id FK -> game_participants.id
  UNIQUE(draw_id, giver_participant_id)
  UNIQUE(draw_id, receiver_participant_id)
  CHECK(giver_participant_id <> receiver_participant_id)

notification_outbox
  id PK
  user_id FK -> users.id
  game_id FK -> games.id NULL
  draw_id FK -> draws.id NULL
  event_type
  payload
  status
  attempts
  next_attempt_at
  last_error
  sent_at
  created_at

audit_logs
  id PK
  actor_user_id
  group_id NULL
  game_id NULL
  action
  created_at
```

**Дополнительные ограничения, требующие реализации:**

- Не более одной текущей игры на группу (частичный unique index по `group_id` для текущих статусов или сериализованная проверка).
- `Assignment` содержит участников той же игры, что и `Draw` (проверка на уровне транзакций/триггеров либо более строгой составной схемы FK).
- Ровно одна активная версия Draw на игру.
- Инвайт используется атомарно: проверка `revoked_at`, `expires_at`, `max_uses` и инкремент `used_count` под блокировкой.

## 10. Надёжность и безопасность

### Идемпотентность

- Дедупликация Telegram Updates по `update_id` там, где требуется.
- `UNIQUE(group_id, user_id)` защищает от повторного вступления.
- `UNIQUE(game_id, user_id)` защищает от повторной регистрации.
- Изменение состояния игры выполняется под блокировкой и с проверкой допустимых переходов.
- Повторное открытие group deeplink не переподтверждает отклонённое участие.

### Доставка

- Сохранение Draw и outbox-событий — в одной DB-транзакции.
- Worker отправляет события после коммита.
- Временные ошибки → retry с backoff и учётом Telegram rate limit.
- Постоянные ошибки (например, пользователь заблокировал бота) → `FAILED` и отображение в статистике доставки.
- Telegram API не даёт транзакционной exactly-once отправки; при неопределённом результате возможны повторные сообщения. Текущая версия жребия всегда определяется БД.
- При новой версии жеребьёвки старые задачи на отправку нужно подавлять/отменять, чтобы не разослать устаревшие назначения.

### Конфиденциальность

- Не публиковать назначения в групповых сообщениях или общих списках.
- Администраторы видят статусы, но не пары «даритель → получатель».
- Не записывать содержимое назначений в обычные логи и аудиторские события.
- Проверять `telegram_id` и права при каждом запросе на просмотр жребия.
- Хранить Telegram Bot Token и webhook secret отдельно от кода.
- Применять HTTPS и проверку webhook secret header.

## 12. План разработки

### Milestone 1 — Инфраструктура и бот

- Создание бота в BotFather.
- Go-проект, конфигурация, миграции PostgreSQL.
- Webhook/long polling, команда `/start`.
- Регистрация пользователей и главное меню.

**Результат:** бот принимает команды и хранит пользователей.

### Milestone 2 — Внутренние группы

- Создание группы и роль Owner.
- Генерация, проверка и отзыв deeplink-приглашений.
- Вступление через ссылку, список групп и участников.
- Роли Owner/Admin/Member, проверки доступа.

**Результат:** несколько независимых групп внутри одного бота.

### Milestone 3 — Игры и подтверждения

- Создание игры, сроки и бюджет.
- Подтверждения существующих членов группы.
- Автоподтверждение нового участника при первом вступлении по deeplink во время регистрации.
- Отказ от участия, закрытие регистрации, списки статусов.
- Идемпотентность повторного вступления по ссылке.

**Результат:** организатор формирует подтверждённый список участников.

### Milestone 4 — Жеребьёвка

- Генерация Random Single Cycle.
- Транзакционное сохранение Draw и Assignment.
- Ограничения, проверка инвариантов, защита от повторного запуска.
- Просмотр собственного результата.

**Результат:** корректная приватная жеребьёвка.

### Milestone 5 — Уведомления

- Transactional Outbox и Worker.
- Личные сообщения с жребием.
- Retry, статусы доставки, защита от устаревших уведомлений.

**Результат:** назначения доставляются с отслеживанием ошибок.

### Milestone 6 — Позднее добавление и пережеребьёвка

- `CONFIRMED + AWAITING_ASSIGNMENT` для новых участников после розыгрыша.
- Подтверждение администратором добавления в текущий Draw.
- Алгоритм минимальной вставки в цикл.
- Полная пережеребьёвка, версии, повторные уведомления.

**Результат:** можно изменять состав после старта без молчаливого изменения жребиев.

### Milestone 7 — Тестирование и production

- Unit-тесты алгоритма и сервисов.
- Integration-тесты с PostgreSQL.
- Тесты конкурентного запуска жеребьёвки, повторного вступления и отзыва приглашения.
- Тесты ошибок Telegram API.
- Docker Compose, CI/CD, мониторинг и резервные копии БД.

## 13. Критерии готовности MVP

1. Один бот обслуживает минимум две независимые внутренние группы.
2. Пользователь может состоять в нескольких группах.
3. Приглашение по deeplink добавляет пользователя именно во внутреннюю группу.
4. Новый член группы при вступлении по ссылке автоматически подтверждён в текущей игре, если её регистрация открыта.
5. Существующие члены группы подтверждают участие в каждой новой игре отдельно.
6. Повторное открытие приглашения не меняет ранее выраженный отказ от участия.
7. Администратор видит состав группы и подтверждения в игре.
8. Жеребьёвка соблюдает все инварианты и не запускается повторно при дублирующемся запросе.
9. Каждый участник видит только собственного получателя.
10. Ошибки доставки сообщений регистрируются и могут быть повторно обработаны.
11. Новый участник после жеребьёвки не меняет назначения без подтверждения администратора.
12. Доступна минимальная вставка и полная пережеребьёвка с версиями Draw.

**Зафиксированное решение v0.3:** внутренние группы не связаны с Telegram-чатами; участники существующей группы должны отдельно подтвердить участие в новой игре; впервые вступивший по group deeplink во время открытой регистрации подтверждается автоматически; после жеребьёвки новое согласие не приводит к автоматической смене назначений — требуется действие администратора.
