# Secret Santa — Go Backend MVP Plan

**Status:** Ready to implement  
**Product source:** [design.md](design.md) (v0.3)  
**Scope:** Backend and Telegram adapter only. No Mini App.

This document freezes the decisions the product design left open, then sequences the work so each milestone is a shippable increment.

## 1. Goal

One Go process family (bot + outbox worker) that:

- talks to users only in a private Telegram chat;
- stores internal groups, games, draws, and delivery tasks in PostgreSQL;
- keeps gift assignments private;
- survives duplicate Telegram updates, double-clicks, and failed sends.

Product rules in `design.md` stay authoritative. This file only says how the Go service implements them.

## 2. MVP boundary

### In

- Long polling locally. Webhook endpoint is structured so production can switch later, but webhook hosting is not part of the first coding pass.
- Users, groups, membership, roles, invites.
- One current game per group.
- Confirm / decline while registration is open.
- Auto-confirm on first join during `REGISTRATION`.
- Random single cycle, minimum 3 participants.
- Own assignment lookup from the database, not from the last message.
- Transactional outbox, retry, cancel of stale sends.
- Minimal cycle insertion of one waiting participant at a time.
- Full redraw.
- Admin delivery stats without recipient names.
- Audit log of admin actions without assignment pairs.

### Out (explicitly later)

- Wishlists, anonymous questions, excluded pairs, history of past pairs.
- Scheduled reminders and a cron that auto-locks at `registration_deadline`.
- Gift-ready confirmation.
- Telegram Mini App.
- Multi-game concurrency inside one group.
- i18n beyond Russian copy.
- Public HTTP API besides Telegram webhook.

The `DRAFT` game status exists in the enum and the transition table, but MVP creates a game directly in `REGISTRATION`. There is no "open registration" step.

## 3. Locked technical choices

| Choice | Decision |
|---|---|
| Module path | `github.com/alekseymakarkin/secret-santa` |
| Go | 1.23+ |
| HTTP / Telegram | `net/http` plus a thin client over Bot API. No bot framework. |
| Postgres driver | `pgx/v5` |
| Queries | `sqlc` |
| Migrations | `goose` SQL files in `db/migrations` |
| Logging | `log/slog`, JSON to stdout |
| Config | environment variables, parsed in `internal/config` |
| IDs | `bigint GENERATED ALWAYS AS IDENTITY` |
| Money | `budget_rub integer NULL`, whole rubles. No currency table. |
| Dates | `registration_deadline timestamptz NULL`, `exchange_on date NULL` |
| RNG | `crypto/rand` Fisher-Yates. No `math/rand`. |
| Invite secret | 16 random bytes, encoded as 22-char base64url (no padding). Only the SHA-256 hash is stored. |
| Processes | `cmd/bot` and `cmd/worker` share `internal/`. Compose runs both. |
| Tests | stdlib `testing`. Integration tests behind `//go:build integration`. |

A framework would hide the update router, callback size limit, and idempotency. Those are the parts that must stay obvious.

## 4. Repository layout

```text
cmd/
  bot/main.go                 # polling loop, HTTP webhook stub
  worker/main.go              # outbox poller
internal/
  config/config.go
  platform/postgres/          # pool, WithTx, goose runner
  domain/                     # entities, enums, sentinel errors, transitions
  users/
  groups/
  games/
  draws/                      # pure cycle math + draw service
  notifications/              # outbox service, worker, message render
  audit/
  telegram/
    updates.go                # dedup, dispatch
    router.go
    screens.go                # text + inline keyboards
    copy.go                   # Russian strings
    session.go                # wizard state adapter
db/
  migrations/
  queries/                    # sqlc input
sqlc.yaml
deploy/
  docker-compose.yml
  Dockerfile
Makefile
```

Dependency rule: `telegram` may call services. Services may call repositories and `domain`. Services must not import `telegram`. `draws` cycle functions must not import `pgx`. Repositories live next to the service that owns the tables (`groups/repo.go`) and are generated by sqlc into `internal/platform/postgres/sqlc`, then wrapped so services see domain types.

One database transaction crosses services only through a `UnitOfWork` passed into the use case that owns the transaction (join, create game, run draw, insert, redraw). Do not open nested transactions.

## 5. Runtime

```text
cmd/bot
  load config
  migrate on startup (local/dev only; production migrates as a release step)
  open pgx pool
  construct services
  loop getUpdates(timeout=30, offset=last+1)
  for each update: handle in its own short transaction, then ack offset

cmd/worker
  every OUTBOX_POLL_INTERVAL (default 1s)
  claim a batch with FOR UPDATE SKIP LOCKED
  send via Bot API
  mark SENT / retry / FAILED
```

Local compose starts Postgres, bot, and worker. The bot does not send assignment messages itself. It only inserts outbox rows.

Polling offset is kept in memory and also written to `bot_offsets` so a restart does not replay the whole history. Replays must still be safe: every handler is idempotent.

## 7. Domain model

Packages use these types. SQL enums use the same spellings.

```text
GroupStatus:     ACTIVE | ARCHIVED
MemberRole:      OWNER | ADMIN | MEMBER
MemberStatus:    ACTIVE | LEFT
GameStatus:      DRAFT | REGISTRATION | LOCKED | DRAWN | COMPLETED | CANCELLED
ParticipantStatus: PENDING | CONFIRMED | DECLINED
AssignmentState: NOT_APPLICABLE | AWAITING_ASSIGNMENT | ASSIGNED
DrawStatus:      ACTIVE | INVALIDATED
OutboxStatus:    PENDING | SENDING | SENT | FAILED | CANCELLED
```

`AssignmentState` is denormalized. It is updated only inside the same transaction that changes the draw. Screens may trust it. The draw service still recomputes invariants from `assignments` before commit.

### Game transitions

Allowed:

```text
DRAFT          -> REGISTRATION | CANCELLED
REGISTRATION   -> LOCKED | CANCELLED
LOCKED         -> DRAWN | REGISTRATION | CANCELLED
DRAWN          -> COMPLETED | CANCELLED
```

`LOCKED -> REGISTRATION` is the admin "reopen registration" escape hatch before a draw exists. Anything else returns `ErrInvalidTransition`.

MVP UI uses `REGISTRATION -> LOCKED -> DRAWN -> COMPLETED` and `-> CANCELLED`. Reopen is implemented in the service so a mistaken lock is recoverable, and exposed as one admin button.

A game in `DRAFT`, `REGISTRATION`, `LOCKED`, or `DRAWN` is **current**. Partial unique index:

```sql
CREATE UNIQUE INDEX games_one_current_per_group
  ON games (group_id)
  WHERE status IN ('DRAFT', 'REGISTRATION', 'LOCKED', 'DRAWN');
```

`COMPLETED` and `CANCELLED` free the group for the next game.

### Participant transitions

While `game.status = REGISTRATION` and (deadline is null or now < deadline):

```text
PENDING  -> CONFIRMED | DECLINED
DECLINED -> CONFIRMED
CONFIRMED -> DECLINED
```

Changing your mind before lock is allowed. After `LOCKED` or `DRAWN`, the participant cannot self-serve. Leave-group rules below are the only other writer.

`assignment_state` writers:

| Event | New state |
|---|---|
| Row created for an existing member at game start | `NOT_APPLICABLE` |
| First join during `REGISTRATION` | `NOT_APPLICABLE` (status `CONFIRMED`) |
| Draw commits, participant included | `ASSIGNED` |
| First join during `DRAWN` | `AWAITING_ASSIGNMENT` (status `CONFIRMED`) |
| Admin inserts that participant | `ASSIGNED` |
| Full redraw includes them | `ASSIGNED` |
| Decline, or leave before draw | `NOT_APPLICABLE` |

### Join matrix

Evaluated only when the user is **not** yet an `ACTIVE` member. If they already are, the handler returns success and does not touch `game_participants`.

| Current game | Membership | Participation |
|---|---|---|
| none, or `COMPLETED` / `CANCELLED` | create `ACTIVE` / `MEMBER` | none |
| `DRAFT` | create member | none |
| `REGISTRATION` (deadline not passed) | create member | `CONFIRMED` + `NOT_APPLICABLE` |
| `REGISTRATION` (deadline passed) | create member | none. Same as locked. |
| `LOCKED` | create member | none. Not added to the closed list. |
| `DRAWN` | create member | `CONFIRMED` + `AWAITING_ASSIGNMENT` |

"First join" means there is no `ACTIVE` membership. A user who `LEFT` and is invited again is treated as a new join for game rules: during `REGISTRATION` they are auto-confirmed; during `DRAWN` they wait for admin insertion. Their old participant row, if the game already has one, is reused only when the unique key collides — see leave rules.

Invite consumption (increment `used_count`) happens on confirmed join, not when the link is merely opened. Opening a link is read-only.

### Leave group

| Game | Effect |
|---|---|
| No current game, or `COMPLETED` / `CANCELLED` | `group_members.status = LEFT`. |
| `REGISTRATION` or `LOCKED` | `LEFT`, and if a participant row exists set it to `DECLINED` + `NOT_APPLICABLE`. |
| `DRAWN` | Reject with `ErrDrawInProgress`. Admin must remove them via redraw or a later removal flow. MVP does not auto-break the cycle. |

The owner cannot leave and cannot be demoted. Transfer ownership first. Archive is owner-only and rejected while a current game exists (`ErrGameInProgress`). Archiving sets `groups.status = ARCHIVED`. Archived groups disappear from "my groups" and reject new joins.

### Roles

Checked in services on every mutation and on every read of admin-only data.

| Action | Owner | Admin | Member |
|---|---|---|---|
| Rename, archive, transfer ownership, grant/revoke admin | yes | no | no |
| Invites, game settings, lock, draw, insert, redraw, delivery stats | yes | yes | no |
| List members, view game card, confirm/decline, view own assignment, leave | yes | yes | yes |

`groups.owner_id` always matches the single `OWNER` row. Transfer updates both in one transaction. There is exactly one owner, enforced by a partial unique index on `(group_id) WHERE role = 'OWNER' AND status = 'ACTIVE'`.

## 8. Draw algorithms

Pure functions in `internal/draws/cycle.go`. They accept and return slices of participant IDs. No I/O.

### `SingleCycle(ids []int64, rng io.Reader) ([]Edge, error)`

Fisher-Yates shuffle with `crypto/rand`, then edge `i -> i+1`, last `->` first.

Errors:

- `len < 3` → `ErrTooFewParticipants` (a 2-cycle would be a mutual pair, which the product forbids).
- duplicate ids → `ErrDuplicateParticipant`.

`Edge` is `{GiverID, ReceiverID int64}`.

Properties covered by tests:

- permutation of the input;
- one edge out and one edge in per id;
- no self-edges;
- exactly one cycle;
- no 2-cycle when `n >= 3` (implied by a single cycle of length >= 3);
- different seeds can produce different rotations and directions.

The distribution is uniform over single cycles, not over all derangements. That is intentional.

### `InsertIntoCycle(edges []Edge, newcomer int64, rng io.Reader) ([]Edge, Edge, error)`

Pick one existing edge `B -> V` uniformly. Replace it with `B -> newcomer` and `newcomer -> V`. Other edges are copied unchanged.

Returns the full new edge list and the **changed** edge identity (`B`, whose receiver changed) so the service can enqueue a message only for `B` and the newcomer.

Errors: empty cycle, newcomer already in the cycle, newcomer id `0`.

Admin warning copy, without names of the pair: one existing participant will get a new recipient; the new participant will receive someone; everyone else keeps their current recipient. The previous recipient may already have been read.

MVP inserts **one** `AWAITING_ASSIGNMENT` participant per admin confirmation. Several waiting people are inserted one by one, each as a new draw version.

### `ValidateCycle(edges []Edge) error`

Run inside the draw transaction before insert. Refuses to commit a set that breaks the invariants, even if the generator is wrong.

## 9. Use cases

Services are small structs with repository interfaces. Signatures below are the contract; names can match Go style (`Create`, `Join`) but the behavior cannot drift.

### Users

`UpsertFromTelegram(ctx, telegramID, username, displayName) (User, error)`

Called at the start of every private update. Sets `dm_started_at` on first sight. `display_name` is `FirstName + LastName` trimmed, falling back to username. Username may be null.

### Groups

- `Create(ctx, actor, name) (Group, InviteLink, error)` — creates group, owner membership, and the first invite in one transaction. Name length 1..80 after trim.
- `ListMine(ctx, actor) ([]GroupCard, error)` — active memberships, not archived groups.
- `GetCard(ctx, actor, groupID) (GroupCard, error)` — member only. Includes member count and current game summary if any.
- `Rename(ctx, actor, groupID, name) error` — owner.
- `Archive(ctx, actor, groupID) error` — owner, no current game.
- `TransferOwner(ctx, actor, groupID, newOwnerUserID) error` — target must be an active member. Old owner becomes `ADMIN`.
- `SetAdmin(ctx, actor, groupID, userID, admin bool) error` — owner. Cannot change the owner row.
- `Leave(ctx, actor, groupID) error` — rules in §7.
- `ListMembers(ctx, actor, groupID) ([]Member, error)`.

### Invites

- `Create(ctx, actor, groupID, opts) (InviteLink, error)` — `opts` is optional `ExpiresAt`, `MaxUses`. Default: no expiry, unlimited uses.
- `List(ctx, actor, groupID) ([]Invite, error)` — admin. Returns metadata only, never the raw token (it was shown once).
- `Revoke(ctx, actor, inviteID) error`.
- `Preview(ctx, rawToken) (GroupPreview, error)` — valid, unexpired, not revoked, uses remaining. Does not increment.
- `Accept(ctx, actor, rawToken) (JoinResult, error)` — the transaction in §10.

Token check: `sha256(rawToken)` lookup. Compare with `subtle.ConstantTimeCompare` on the hash bytes. Start payload is `join_<token>`. `join_` (5) + 22 token chars fits Telegram's 64-char start limit.

### Games

- `Create(ctx, actor, groupID, spec) (Game, error)` — admin. Inserts the game as `REGISTRATION` and a `PENDING` / `NOT_APPLICABLE` participant for every `ACTIVE` member, including the creator. Fails with `ErrCurrentGameExists` if the partial unique index trips.
- `Get(ctx, actor, gameID) (GameCard, error)` — member of the group. Counts by status. Admin flag so the UI can add buttons; the flag is not authorization by itself.
- `SetParticipation(ctx, actor, gameID, status) error` — `CONFIRMED` or `DECLINED` only, under the rules in §7.
- `ListParticipants(ctx, actor, gameID) ([]Participant, error)` — member. No assignment pairs.
- `Lock(ctx, actor, gameID) error` — admin, from `REGISTRATION`.
- `Reopen(ctx, actor, gameID) error` — admin, from `LOCKED` only.
- `Complete(ctx, actor, gameID) error` — admin, from `DRAWN`.
- `Cancel(ctx, actor, gameID) error` — admin, from any non-terminal status. Cancels pending outbox rows for that game. Does not reveal assignments.

`spec`: name (1..80), `BudgetRub *int` (nil or 1..1_000_000), `RegistrationDeadline *time.Time`, `ExchangeOn *date`. Deadline must be in the future if set. Exchange day, if both set, must be on or after the deadline's calendar day in UTC.

### Draws

- `Run(ctx, actor, gameID) (Draw, error)` — admin. Status must be `LOCKED` or `REGISTRATION`. If still `REGISTRATION`, lock it in the same transaction (admin confirmed; do not require a separate prior click beyond the confirm button). Participants: `CONFIRMED` and active members only. Count >= 3. See transaction in §10.
- `ViewMine(ctx, actor, gameID) (AssignmentView, error)` — caller must be an `ASSIGNED` participant. Returns only their receiver display name, budget, exchange day, game name. `ErrNotAssigned` if they are waiting or declined.
- `ListWaiting(ctx, actor, gameID) ([]Participant, error)` — admin. `AWAITING_ASSIGNMENT` only.
- `Insert(ctx, actor, gameID, participantID) error` — admin. One waiting participant. New draw version.
- `Redraw(ctx, actor, gameID) error` — admin. New cycle over everyone who is `CONFIRMED` and (`ASSIGNED` or `AWAITING_ASSIGNMENT`) and still an active member.

`Run` is not valid twice for the same game state. A second call finds `DRAWN` and returns `ErrAlreadyDrawn` without writing. Insert and redraw are explicit different methods, so a retried "run" callback cannot redraw.

### Notifications

- `EnqueueAssignment(tx, user, game, draw, kind, view)` — called only from draw transactions.
- `ClaimBatch(ctx, n) ([]Job, error)`
- `MarkSent(ctx, id) error`
- `MarkRetry(ctx, id, after time.Time, err string) error`
- `MarkFailed(ctx, id, err string) error`
- `Stats(ctx, actor, gameID) (DeliveryStats, error)` — admin. Counts by status plus per-recipient **sender** display name and last error class. Payload is not selected.

`kind`: `ASSIGNMENT_CREATED`, `ASSIGNMENT_CHANGED`, `ASSIGNMENT_REDRAWN`.

Worker policy:

| Bot API result | Outbox |
|---|---|
| 200 | `SENT` |
| 429 | `PENDING`, `next_attempt_at = now + retry_after` |
| 5xx, timeout, network | `PENDING`, exponential backoff capped at 15m: 5s, 15s, 1m, 5m, 15m |
| 403 blocked / chat not found | `FAILED` |
| attempt count > 8 | `FAILED` |

Sending rows stuck in `SENDING` older than 2 minutes are reclaimed (process crashed after claim). That can duplicate a message. The product accepts this. The database remains the source of truth; `ViewMine` shows the active draw.

### Audit

`Record(tx, actor, groupID, gameID, action)` where `action` is a short code (`group.created`, `invite.revoked`, `game.locked`, `draw.created`, `draw.inserted`, `draw.redrawn`, `member.role_changed`). No JSON payload with names of receivers.

## 10. Transactions that must be correct

### Accept invite

```text
BEGIN
  SELECT invite FOR UPDATE
  reject if revoked, expired, or used_count >= max_uses
  upsert user already done
  SELECT membership
  if ACTIVE: commit without changes (idempotent success)
  if LEFT: set ACTIVE, role MEMBER, refresh joined_at
  else INSERT member
  increment used_count
  apply join matrix against the current game (SELECT game FOR UPDATE)
COMMIT
```

A revoked invite cannot win a race against accept. The row lock serializes revoke and accept.

### Create game

```text
BEGIN
  SELECT group FOR UPDATE
  reject if a current game exists
  INSERT game REGISTRATION
  INSERT participant PENDING for each ACTIVE member
  audit
COMMIT
```

The partial unique index is the backstop if the lock is forgotten.

### Run draw

```text
BEGIN
  SELECT game FOR UPDATE
  reject unless status in (REGISTRATION, LOCKED)
  reject unless actor is owner or admin and an active member
  load CONFIRMED participants who are ACTIVE members
  reject if count < 3
  edges = SingleCycle(...)
  ValidateCycle(edges)
  nextVersion = coalesce(max(version), 0) + 1
  INSERT draw ACTIVE
  INSERT assignments
  UPDATE those participants SET assignment_state = ASSIGNED
  INSERT outbox ASSIGNMENT_CREATED for each giver
  UPDATE game SET status = DRAWN, active_draw_id = draw.id
  audit draw.created
COMMIT
```

`active_draw_id` is a nullable FK added without a circular insert problem: the draw row exists before the game update. `ON DELETE RESTRICT`.

Exactly one active draw:

```sql
CREATE UNIQUE INDEX draws_one_active_per_game
  ON draws (game_id)
  WHERE status = 'ACTIVE';
```

### Insert one participant

```text
BEGIN
  SELECT game FOR UPDATE
  require status DRAWN and active_draw_id
  lock participant, require CONFIRMED + AWAITING_ASSIGNMENT
  load active draw edges
  newEdges, changed = InsertIntoCycle(...)
  ValidateCycle(newEdges)
  invalidate old draw (status INVALIDATED)
  cancel outbox rows for old draw where status in (PENDING, SENDING)
  insert new draw version ACTIVE, copy unchanged edges, write the two new edges
  set newcomer ASSIGNED
  enqueue ASSIGNMENT_CHANGED for the changed giver
  enqueue ASSIGNMENT_CREATED for the newcomer
  point game.active_draw_id at the new draw
  audit draw.inserted
COMMIT
```

Rows already `SENT` are left as history. They are not edited. The changed giver gets a new message that their recipient was updated.

### Full redraw

Same locking. Build `SingleCycle` over assigned **and** awaiting confirmed active members. Invalidate old draw, cancel unsent old notifications, enqueue `ASSIGNMENT_REDRAWN` for every participant in the new cycle, set all of them `ASSIGNED`.

### Assignment FK integrity

`assignments` stores `game_id` denormalized and uses composite foreign keys:

```text
giver_participant_id, game_id  -> game_participants(id, game_id)
receiver_participant_id, game_id -> game_participants(id, game_id)
draw_id, game_id -> draws(id, game_id)
CHECK (giver_participant_id <> receiver_participant_id)
UNIQUE (draw_id, giver_participant_id)
UNIQUE (draw_id, receiver_participant_id)
```

This makes a cross-game assignment unrepresentable. `game_participants` needs `UNIQUE (id, game_id)` (id is already PK; add the extra unique for the composite FK). Same for `draws(id, game_id)`.

## 11. Telegram adapter

Private chats only. Ignore group and channel updates.

### Update pipeline

1. Drop update if `processed_updates` already has `update_id` (insert-on-handle, unique PK).
2. Resolve `from`. Ignore if missing.
3. `Users.UpsertFromTelegram`.
4. If `message.text` starts with `/start`, clear wizard session and handle start.
5. Else if a non-expired session exists and the message is text, feed the wizard.
6. Else if `callback_query`, parse, authorize, dispatch, `answerCallbackQuery`.
7. Else show the main menu.

`answerCallbackQuery` always runs, including on error, so the client stops the spinner. Failures edit the message or send a short Russian error.

Unknown callback or a stale id returns "Это действие больше недоступно" and does not mutate.

### Start payload

| Payload | Behavior |
|---|---|
| empty | main menu |
| `join_<token>` | `Invites.Preview`. Show group name and `[Вступить]`. Do not join yet. |
| anything else | main menu plus "Ссылка недействительна." |

The join button's callback carries the invite id (`inv:accept:<inviteID>`), not the raw token. Preview stores nothing. Accept loads the invite by id, but still re-checks revoked/expiry/uses under lock. Binding the button to the invite id avoids putting the secret in callback data. If the invite was recreated, the old button fails closed.

### Wizard sessions

Table `bot_sessions(user_id PK, state, context jsonb, updated_at)`.

| State | Expects | Writes |
|---|---|---|
| `group_name` | text | `Groups.Create`, then group card |
| `game_name` | text | context `group_id`, next state `game_budget` |
| `game_budget` | integer rubles, or `-` to skip | next `game_deadline` |
| `game_deadline` | `DD.MM.YYYY` or `-` | next `game_exchange` |
| `game_exchange` | `DD.MM.YYYY` or `-` | `Games.Create`, then game card |
| `group_rename` | text | `Groups.Rename` |

Any `/start` or `Отмена` clears the session. Sessions older than `SESSION_TTL` are ignored and deleted.

Match `design.md` §11. Extra admin buttons are attached only when the service says the actor is owner or admin **and** the game status allows the action. Hiding a button is not the permission check.

Copy lives in `internal/telegram/copy.go`. User-facing errors map from sentinel errors:

| Error | Text |
|---|---|
| `ErrForbidden` | Недостаточно прав. |
| `ErrNotMember` | Ты не состоишь в этой группе. |
| `ErrInviteInvalid` | Ссылка недействительна или отозвана. |

- `group_invites.token_hash bytea UNIQUE` (raw sha256).
- `games.budget_rub`, `games.registration_deadline`, `games.exchange_on`, `games.updated_at`.
- `games.active_draw_id` FK to `draws(id)` DEFERRABLE INITIALLY DEFERRED is unnecessary if we insert the draw first. Use a plain nullable FK.
- composite uniques and FKs from §10.
- partial uniques: one current game, one active draw, one active owner.
- `notification_outbox.payload jsonb NOT NULL`. No assignment data in other tables' text columns.
- `processed_updates(update_id bigint PK, processed_at timestamptz)`.
- `bot_offsets(id int PK CHECK (id = 1), update_offset bigint)` single row.
- `bot_sessions` as in §11.
- `audit_logs.action text`, no payload column in MVP. If a detail is required later, add a column that is forbidden from containing recipient ids.

Indexes for the worker:

```sql
CREATE INDEX notification_outbox_due
  ON notification_outbox (next_attempt_at)
  WHERE status IN ('PENDING', 'SENDING');
```

Claim query:

```sql
UPDATE notification_outbox o
SET status = 'SENDING', attempts = attempts + 1
WHERE id IN (
  SELECT id FROM notification_outbox
  WHERE status = 'PENDING' AND next_attempt_at <= now()
  ORDER BY next_attempt_at
  FOR UPDATE SKIP LOCKED
  LIMIT $1
)
RETURNING *;
```

Migrations are ordered and append-only:

1. `00001_users.sql`
2. `00002_groups.sql` — groups, members, invites
3. `00003_games.sql` — games, participants
4. `00004_draws.sql` — draws, assignments, then `games.active_draw_id`
5. `00005_notifications.sql`
6. `00006_audit_sessions_updates.sql`

## 13. Confidentiality checklist

- Logs include `update_id`, `user_id`, `group_id`, `game_id`, `draw_id`, `event_type`, error class. Never `payload`, token, bot token, or giver/receiver pair.
- `Stats` SQL must not select `payload`.
- Member lists and participant lists do not join `assignments`.
- `ViewMine` filters `giver participant.user_id = actor` in SQL, not in Go after fetching the whole draw.
- Audit actions listed in §9 are the only ones written.
- Tests fail the build if a log test helper sees the substring of a known receiver paired with a giver. One focused test on the draw service logger is enough.

## 14. Testing

### Unit (no database)

- `SingleCycle` and `InsertIntoCycle` property tests, 1000 iterations, n from 3 to 20.
- `ValidateCycle` rejects self-edge, duplicate giver, two cycles, and a swap of two people.
- Game and participant transition tables.
- Join matrix table.
- Callback parser: accept the catalog in §11, reject overflow, reject unknown verbs.
- Start payload parser.
- Outbox backoff and error classification with a fake Bot API.

### Integration (`make test-integration`, Postgres from compose)

- Create two groups, one user in both, invites do not cross.
- Accept is idempotent; decline survives a second accept.
- First join during `REGISTRATION` confirms; existing member stays `PENDING` when a game is created.
- First join during `LOCKED` creates no participant.
- First join during `DRAWN` is `AWAITING_ASSIGNMENT` and does not change edges.
- Concurrent `Run`: one winner, one `ErrAlreadyDrawn`, one active draw.
- Insert changes exactly one old giver and keeps every other edge.
- Redraw invalidates version 1, cancels its pending outbox, writes version 2.
- Revoke versus accept under two transactions: revoked invite never increments.
- `ViewMine` for user A does not return user B's receiver.

Use a real Postgres (compose service `postgres:16`). Do not mock SQL for these. sqlc queries are the thing under test.

### Fixtures

A `internal/telegram/fake` Bot API client records outgoing texts for worker tests. It can return 429, 403, and 500.

## 16. Manual script for the last slice

Run against two Telegram accounts (or one account plus a second client):

1. A creates "Friends" and "Colleagues".
2. B opens only the Friends link and joins. B is not in Colleagues.
3. A creates a game in Friends. A is `PENDING`. B, who joined before the game, is also `PENDING`.
4. C joins during registration and is auto-confirmed. B declines. A confirms. A third member D joins and is auto-confirmed. A locks and draws (A, C, D).
5. B still has no assignment. B's decline survives opening the link again.
6. Each of A, C, D sees only their own receiver. Admin delivery screen shows three sends and no pair.
7. E joins after the draw. Edges do not change until A confirms insertion. Exactly one previous giver is notified of a change.
8. A runs a full redraw. A new draw version is active. Old pending sends are cancelled.

## 17. Implementation order inside a slice

When a slice is picked up:

1. Migration and sqlc query.
2. Domain error / transition, with a unit test.
3. Service method and repository.
4. Integration test for the invariant that slice claims.
5. Telegram screen and callback last.

UI-last keeps the database rules testable without parsing message text.

## 18. Risks

| Risk | Mitigation |
|---|---|
| Circular FK between `games` and `draws` | Insert draw, then set `active_draw_id`. |
| Callback data over 64 bytes | Decimal int64 and short verbs. No UUIDs in buttons. |
| Start payload too long | 22-char token. |
| Double draw | `SELECT FOR UPDATE` plus partial unique active draw plus status check. |
| Stale assignment message after redraw | Cancel `PENDING`/`SENDING` for the old draw in the same transaction. |
| Admin learns a pair from delivery stats | Stats query does not read `payload`. |
| Owner stuck | Transfer ownership before leave. Leave of owner is `ErrForbidden`. |
| Deadline passes with no worker | Enforced lazily on confirm and on join. No scheduler in MVP. |

## 19. Definition of done

The backend MVP is done when the twelve acceptance criteria in `design.md` §13 pass by the tests in §14 and the manual script in §16, and when logs and admin queries cannot show a giver-receiver pair to anyone but the giver.
